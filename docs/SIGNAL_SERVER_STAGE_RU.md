# Серверная основа Signal: устройства и prekeys

Миграция 20261115034416_signal_device_prekeys.sql добавляет новый изолированный контракт. Существующие e2ee_* и chat_messages не изменяются. При развёртывании app_private.signal_rollout был пуст. Для клиентского этапа beta17 пользователь указал два тестовых аккаунта; допуск включён только им. Остальные клиентские Signal RPC закрыты. Разрешение нельзя включить из приложения.

## Контракт

- signal_register_device: JWT-владелец, установка UUID, слот1–127, registration1–16380, identity33bytes и подписанный prekey. Точный повтор идемпотентен; замена идентичности/подписанного ключа запрещена. Разрешено одно активное устройство: добавление второго требует будущего отдельного механизма подтверждения. После отзыва номер слота повторно не используется.
- signal_publish_prekeys: пары одноразовых EC/PQ ключей (33/1569bytes, подпись64bytes), пакет1–100, максимум1000 доступных/10000 всего на устройство. Точный повтор загрузки ничего не перевыпускает, даже если ключ уже выдан. Любая ошибка откатывает весь пакет.
- signal_claim_bundle: проверяет допуск обеих сторон, взаимную дружбу и блокировки; атомарно помечает одну пару использованной через FOR UPDATE SKIP LOCKED. request UUID сохраняется с выданным публичным bundle; повтор возвращает тот же bundle, а изменение адресата того же request отклоняется. Лимит30 новых запросов в минуту/5000 квитанций на пользователя. Транзакция должна быть READ COMMITTED. Отзыв устройства проверяется до выдачи сохранённой квитанции.
- signal_list_devices: собственные или доступные устройства друга; не раскрывает одноразовые ключи.
- signal_revoke_device: только свой слот и installation UUID; повтор безопасен.

Прямые SELECT/INSERT/UPDATE/DELETE/TRUNCATE новых таблиц запрещены PUBLIC/anon/authenticated, RLS включён. RPC только authenticated, SECURITY DEFINER с пустым search_path и обязательной проверкой auth.uid/допуска. Helper-функции приватны.

## Границы безопасности

Сервер проверяет форму, размеры и владение аккаунтом по JWT, но не криптографическую правильность подписей. Подписи обязан проверить libsignal SessionBuilder; доверие к новым идентичностям устройств требует отдельного подтверждения клиента. JWT не является доказательством владения приватным ключом устройства. Связывание устройств, ротация подписанного ключа, восстановление архива, очистка квитанций/лимитов и реальная доставка ещё не подключены. Живые ratchet snapshots не загружаются на сервер. Контракт API предусматривает только публичные ключи и подписи; приватные ключи клиент отправлять не должен.

## Проверки

`python tools/test_signal_server.py --pg-bin <каталог PostgreSQL bin>` сам создаёт отдельный localhost-кластер с синтетическими пользователями, применяет миграцию и останавливает только этот кластер. Строка подключения к существующей БД не принимается. Проверены права anon/authenticated, закрытый rollout, неизменность устройства, ошибочные batch rollback, повторная загрузка использованного ключа, дружба/блокировка/отзыв и квота. Гонки: 8 повторов одного request дали один ключ, 12 разных запросов и 8 запросов от разных аккаунтов дали разные ключи. Размеры публичных ключей сверены с libsignal9.0.0 отдельным Flutter-тестом.

## Развёртывание

Миграция применена через Supabase MCP 15.11.2026; номер20261115034416 взят из фактической истории сервера. Локальный файл, первоначально созданный CLI, переименован под этот номер без изменения SQL, чтобы последующий db push не пытался повторить схему. На сервере подтверждены RLS, отсутствие SELECT/INSERT/TRUNCATE у authenticated, запрет EXECUTE для anon и нулевой допуск/ноль устройств. Проверка под authenticated с синтетическим sub в откатываемой транзакции получила SIGNAL_ROLLOUT_DISABLED. Реальные пользователи не включались; их сообщения и ключи не читались.

Мобильный код и версия APK не менялись: серверный контракт пока недоступен приложению. Следующий этап — клиентская регистрация устройства/публикация prekeys, криптографическая проверка полученного bundle и согласованное включение протокола для тестовой пары.

Итоговая проверка: локальный PostgreSQL17.12 и серверный шаг Linux CI прошли, полный CI43673880688 success (коммит ece33cd7d49f038f0eea38b37454c90018ef4803). Эффективные SELECT/INSERT/UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER для anon/authenticated на всех четырёх таблицах проверены: разрешённых операций нет. Действующая мобильная версия остаётся beta16+127; нового APK в этом серверном этапе нет.

## Клиент beta17

Независимый E2EE_SIGNAL_REGISTRY включает экран регистрации в настройках конфиденциальности. Сервис signal_device_registry.dart сначала сохраняет installation UUID, приватные записи и 20 одноразовых пар, затем вне SQL-транзакции вызывает register/publish/list. Точные повторы не создают новых ключей; ответ сверяется с локальной identity. Claim adapter требует заранее одобренный ключ и проверяет контекст и обе подписи bundle, но к транспорту реальной переписки пока не подключён. Два тестовых допуска включены по явному выбору пользователя; серверных устройств на момент публикации ещё0, физический телефон заблокирован.
