# Раунд 4: идемпотентность и надёжность клиентских операций E2EE при сбоях

Дата: 10.11.2026. Read-only аудит ветки codex/chat-e2ee (HEAD d838929).
Только код-трассировка и локальные мок-тесты (без production/сети/реальных
аккаунтов). Не повторяет раунды: гонка блокировки (задача 1), push (задача 2),
RLS/триггеры, криптоалгоритм (раунд 2), локальное хранение (раунд 3).
Тесты — на ветке codex/send-retry-idempotency.

## Вердикт

Дубликатов серверных строк, потери сообщений и ложной доставки при
рассмотренных сбоях не обнаружено; идемпотентность повтора доказана тестами.
Два минорных сценария отображения (C1, C2) задокументированы, оба
самовосстанавливаются, фиксы не применялись (затрагивают UI-семантику).

## Сценарии (файлы:строки, вердикт)

1. **Send/retry после тайм-аута, когда сервер принял** — идемпотентно:
   повтор идёт с тем же клиентским messageId → fetchMessage → return existing
   (chat_service.dart:254-261, E2EE-ветка; messageId генерируется всегда
   :253); конфликт PK 23505 → fetch-фолбэк (:372-380). Тест 1: retry после
   принятого insert → ровно 1 insert на проводе. Тест 2: 409/23505 →
   возвращается сохранённая строка, ничего не персистится повторно
   (e2ee_send_retry_idempotency_test.dart, 2 passed). Попутно подтверждено
   условие `messageId != null` в 23505-ветке (:373): без клиентского id
   (legacy без id) фолбэк недостижим — но и конфликт тогда невозможен.
2. **Double-tap отправки** — опровергнуто: _sendMessage синхронен до очистки
   ввода (:909-975: для текста await нет, setState+clear :970-975) — второй
   тап получает пустой ввод и выходит; double-tap failed-bubble: onTap активен
   только при delivery==failed (:1632, :1788), первый тап ставит sending
   (:1082-1087) → onTap null.
3. **Дубликаты realtime-событий** — опровергнуто: insert-дедуп `_delivered`
   (:1212-1215); update-события без дедупа, но идемпотентны (callback →
   _merge по id, chat_screen.dart:300-311 — свежее перекрывает старое);
   delete-события идемпотентны (_onDeleted, :163-167, 1917+). Оптимистичная
   копия и realtime-копия одного id сливаются _merge'ом — визуальных
   «двойников» нет.
4. **Offline-очередь** — pending персистится с delivery=sending (:977), сбой →
   failed (:1110-1123); после process death reload помечает sending→failed
   (chat_local_store.dart:50-53); автоповтора чата нет — ручной retry без
   потери текста и без автодублей.
5. **Пагинация** — keyset-курсор `before` с tie-break по id
   (chat_service.dart:527-531); guard `_loadingPage` (chat_screen.dart:356);
   merge сохраняет pending/failed и старые страницы (:379-390); refresh
   согласует удаления только в свежем окне (:383-392). Скипов/дублей нет.
6. **Восстановление после process death** — кэш reload → failed → ручной
   retry → dedup п.1. Ложной доставки нет: sent ставится только из ответа
   сервера (:1104-1109).
7. **Edit** — повтор идемпотентен: update payload по id+sender
   (chat_service.dart:679-686), guard сервера sender-only; тайм-аут → повтор
   создаёт новый envelope → заменяет payload; дублей/потери нет.
8. **Reply** — replyToId — метаданные; retry ответа из push имеет
   детерминированный id из SHA-256 (notification_identity.dart:5-15) →
   OS-повтор дедупится тем же механизмом п.1.
9. **Read** — update с `read_at is null` (:738-745, :759-765): повтор
   идемпотентен, сбой → false → ложного прочтения нет.
10. **Delete** — удаление по id+sender (:789-795), double-tap закрыт диалогом
    подтверждения. Минорный сценарий C2: тайм-аут delete при фактическом
    удалении + пропуск realtime-DELETE → «ghost» локально до refresh; повтор
    → existing==null → false («не ваше или сети нет»). Серверная семантика
    корректна; самовосстановление через reload/refreshAttachment.

## Задокументированные минорные сценарии (фиксы не применялись)

- **C1 (false-failed, self-healing)**: успешная отправка при смене аккаунта
  mid-flight → _transmit возвращает false ПОСЛЕ успеха (:1107) → pending
  остаётся sending → после reload помечается failed, хотя сервер подтвердил.
  Retry тем же messageId восстанавливает sent (dedup п.1); серверных дублей
  нет. Окно миллисекунды; фикс менял бы UI-семантику смены аккаунта.
- **C2 (ghost после delete-тайм-аута)** — см. п.10; фикс менял бы семантику
  удаления → не применён по условиям раунда.

## Ограничения

- Флаг E2EE_MESSAGING compile-time: в тестах выключен; retry/23505-механика
  общая для обеих веток sendMessage (E2EE-ветка :244-289 использует те же
  шаги), но E2EE-специфичный локальный прогон невозможен.
- Поведение FK reply_to_id при удалённой цели — базовая схема сервера не в
  репо, не проверено.
- Realtime-канал в тестах не мокировался (SDK-уровень); дедуп-инварианты
  подтверждены кодом.
