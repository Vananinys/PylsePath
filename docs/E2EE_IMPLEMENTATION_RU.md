## Решения пользователя

- Чаты должны шифроваться по умолчанию, без отдельного режима и без скрытой
  отправки открытого текста при ошибке или старом клиенте.
- Восстановление через личный случайный ключ, который хранит пользователь.
  Сервер не получает открытый ключ восстановления или приватные ключи.

## Реализовано отдельно от работающего чата

- E2eeRecoveryVault: контейнер AES-256-GCM, случайный 256-битный ключ,
  новый nonce при каждой записи, привязка к аккаунту через authenticated data.
  Контейнер предназначен для резервной копии секретов, не является протоколом
  обмена сообщениями. Код восстановления нельзя включать в серверный контейнер.
- E2eeSecretStore: защищённое платформенное хранилище отдельно по аккаунтам,
  проверка владельца вокруг асинхронных операций, подтверждение записи,
  последовательные записи одного экземпляра без открытого fallback.
  Проверка чтением не гарантирует fsync; этот класс нельзя использовать как
  готовый ratchet-store. Для сессий нужен отдельный атомарный durable слой.
- Зависимости закреплены. Версия flutter_secure_storage 11.2.0 конфликтует
  с share_plus 12.0.2 по win32; используется совместимая 10.3.4.

Эти классы пока не вызываются из чата. Ключи реальных пользователей не созданы,
старая история и её формат не изменены.

## Что требуется до включения и выпуска

1. Добавлен libsignal 9.0.0: на Windows прошли генерация независимых identities,
   реальный обмен и ответ, отказ при подмене ciphertext/повторе сообщения,
   чтение подлинного ответа после подмены и доставка не по порядку.
   Проверить реализацию установленного протокола (Signal/MLS),
   включая поддержку Android/iOS/Web, лицензию, персистентность и атомарность
   ratchet-состояния. Не заменять протокол самодельным обменом статическими ключами.
2. Серверный реестр устройств, подписанные и одноразовые prekeys, атомарная выдача,
   RLS и запрет подмены владельца. Верификация отпечатков, явное предупреждение
   о смене ключа. TOFU не защищает первый контакт от злонамеренного сервера.
3. Версионированный ciphertext-конверт с привязкой к ID сообщения, отправителю,
   получателю, устройствам и типу содержимого. Все пути отправки должны использовать
   его: текст, стикеры, фото, голос, видео/превью, маршруты, посты и приглашения.
4. Проверить клубные/групповые чаты отдельно: состав, исключение участника,
   ротация ключей, новые устройства. Нельзя считать личный чат защитой клубного.
5. Шифрование самих файлов до загрузки, метаданные/ключи файлов только внутри
   конверта. Безопасное воспроизведение, ограниченный локальный кэш; исходные
   и расшифрованные копии также требуют защиты на устройстве.
6. Локальные очередь, черновики, история и резервные копии: защищённое хранение,
   миграция без потери исходников. Отдельно решить защиту GPS и пользовательских
   мест; публичные публикации не становятся конфиденциальными от E2EE чатов.
7. Push: только нейтральное уведомление, без текста, медиа и ключей. Проверить
   серверный обработчик и фоновый процесс, не только Flutter UI.
8. Восстановление на новом устройстве с личным ключом, подтверждение сохранения
   ключа, проверка подлинности резервной копии; восстановление identity само
   по себе не восстанавливает уже удалённые ratchet-ключи/историю.
9. Совместимость: старую историю сохранить с честной пометкой; новая отправка
   только зашифрованная, старому клиенту нужна понятная просьба обновиться.
   Серверный запрет открытых новых сообщений вводить после проверки готового
   клиента. Отдельно мигрировать редактирование, поиск, Realtime и повтор отправки.
10. Проверить две независимые установки, несколько устройств, офлайн/повторы,
    восстановление, повреждения, смену аккаунта и ключей, блокировки, членство.
    Затем APK, подпись, стабильный выпуск, каталог, серверный push и телефон
    по docs/GIT_AND_RELEASES_RU.md. Незавершённую основу не публиковать как E2EE.

## Проверка сервера 10.11.2026

Read-only: chat_media — приватный бакет; в chat_messages есть политики доступа
участников, отправки друзьям, блокировок и ограничительные guards. Изучены
триггеры: поля вложений и приглашений валидируются сервером; редактирование body
ограничено 4000 символами. Подстановка ciphertext в body без миграции ломает
лимиты и не защищает остальные поля. Push запускается серверным триггером.
Политики сами по себе не доказывают отсутствие всех утечек или наличие E2EE.
